# MiniMax 用量小组件与详情应用设计

- 日期：2026-07-22
- 状态：已确认
- 目标平台：Windows 10 x64
- 首版服务：MiniMax Coding Plan

## 1. 背景与结论

当前项目是一个 Rainmeter 桌面用量小组件：PowerShell 定时调用 MiniMax API，将标准化后的当前额度写入项目目录，Rainmeter 只读取缓存并展示。

本次改造的目标是保留现有轻量采集方式，同时把最终体验升级为：

1. 常驻桌面的双圆环额度小组件；
2. 点击小组件后按需打开独立 Windows 详情 EXE；
3. 详情窗口展示当前额度、重置时间和本机记录的额度变化趋势；
4. 首版只接 MiniMax，但数据结构允许未来增加其他服务；
5. 不要求用户安装 Node.js、Python 或 .NET 运行时。

结论：该目标可实现，并且不需要推翻当前 API、DPAPI、任务计划和缓存链路。

## 2. 参考项目调研

### 2.1 ccusage 的功能

调研基于 ccusage 20.0.18、仓库提交 `31e084a`。

ccusage 的核心能力包括：

- 读取 Claude Code、Codex、Kimi 等 Coding Agent 的本地使用记录；
- 按日、周、月和会话聚合 Token 与费用；
- 输出统一报表、单服务报表、5 小时窗口和状态栏信息；
- 支持 JSON 输出、模型拆分、日期过滤、时区和窄终端紧凑模式；
- 通过各服务独立 Adapter 兼容不同日志位置和格式。

### 2.2 ccusage 的代码设计

ccusage 当前以 Rust 为核心，npm 包只负责启动对应平台的原生二进制：

- `apps/ccusage/src/cli.js`：选择并启动原生包；
- `rust/crates/ccusage-cli`：命令参数与帮助；
- `rust/crates/ccusage-terminal`：颜色、宽度计算和响应式表格；
- `rust/crates/ccusage`：各服务 Adapter、解析、聚合、费用和输出；
- `rust/crates/ccusage/src/adapter/<provider>`：每个服务独立的路径、加载、解析和报表逻辑。

可借鉴的核心思想是：

```text
来源适配 → 统一数据 → 聚合处理 → 多种展示
```

不应直接照搬的部分：

- ccusage 面向本地 Coding Agent 日志，当前项目的数据来自 MiniMax 额度 API；
- ccusage 的官方界面是终端表格，三张参考图是桌面 GUI 风格，不是其原生 UI；
- 当前项目只有一个服务，不应提前复制 ccusage 的完整多 Provider 框架。

本项目只采用最小的可扩展数据契约，不提前实现未使用的 Provider Adapter。

## 3. 已确认的产品范围

### 3.1 常驻桌面小组件

采用双圆环并列布局：

- 左圆环：5 小时剩余额度；
- 右圆环：本周剩余额度；
- 圆环中央显示剩余百分比；
- 圆环下方分别显示窗口名称和重置倒计时；
- 顶部显示套餐名和数据状态；
- 底部显示更新时间和“查看详情”；
- 点击“查看详情”按需启动详情 EXE。

小组件继续由 Rainmeter 承载，不增加常驻后台应用。

### 3.2 Windows 详情应用

采用 WPF 与 .NET 8，发布为 `win-x64` 自包含单文件 EXE。

详情窗口包含：

- MiniMax Coding Plan 标题和当前数据状态；
- 5 小时、本周两个大圆环；
- 两个窗口的准确重置时间和相对倒计时；
- 最后成功更新时间；
- 24 小时、7 天、30 天额度趋势切换；
- 手动刷新按钮（复用现有 PowerShell 采集流程）；
- 数据来源及口径说明；
- 错误或数据过期提示。

EXE 按需启动，关闭窗口后进程完全退出，不驻留系统托盘。

### 3.3 明确不在首版范围内

- 不接入 Claude、Codex、Kimi 等其他服务；
- 不展示空的其他服务卡片；
- 不声称拥有精确 Token 消耗数据；
- 不实现账号登录、云同步或远程数据库；
- 不让详情 EXE 读取 API Key 或直接调用 MiniMax API；
- 不实现托盘常驻、通知、自动更新或复杂动画；
- 不复制 ccusage 的完整日志解析和费用计算系统。

## 4. 系统架构

```text
MiniMax API
    │
    ▼
Update-MinimaxUsage.ps1
    ├─ DPAPI 解密 API Key
    ├─ 请求、重试、校验与标准化
    ├─ 写当前状态 cache.json
    ├─ 写 Rainmeter 简单文本缓存
    └─ 追加成功的额度历史 history.jsonl
              │
              ├─────────────┐
              ▼             ▼
       Rainmeter 小组件   WPF 详情 EXE
       只读简单文本       只读 cache/history
```

设计约束：

- PowerShell 是唯一的数据采集者和写入者；
- Rainmeter 与 WPF 均为只读展示层；
- API Key 只在 PowerShell 进程中短暂解密；
- 当前状态继续原子写入，避免展示层读取半截 JSON；
- API 调用失败时不覆盖最后一次成功额度；
- WPF 打开期间定时重新读取本地缓存，不主动联网。

## 5. 数据设计

### 5.1 当前状态 `cache.json`

缓存升级到 `schema_version: 2`，保留现有字段以减少对现有脚本的影响，并增加稳定标识：

```json
{
  "schema_version": 2,
  "provider_id": "minimax",
  "status": "ok",
  "plan": "MiniMax TokenPlan",
  "last_update": "2026-07-22T11:11:36+08:00",
  "error": null,
  "items": [
    {
      "model_id": "general",
      "window_id": "5h",
      "name": "文本 (5小时)",
      "remaining_pct": 76.0,
      "reset_at": "2026-07-22T14:20:00+08:00",
      "reset_text": "2小时18分后"
    },
    {
      "model_id": "general",
      "window_id": "weekly",
      "name": "文本 (周)",
      "remaining_pct": 89.0,
      "reset_at": "2026-07-26T00:00:00+08:00",
      "reset_text": "4天后"
    }
  ]
}
```

`provider_id`、`model_id` 与 `window_id` 用于避免 UI 依赖中文显示名称。首版明确只展示 Coding Plan 对应的 `general` 文本模型；即使 API 同时返回视频模型，也不会因数组顺序而误用其额度。未来增加服务时，新数据源只需转换为同一份内存数据形状；首版不实现多 Provider 文件发现或未使用的复杂抽象层。

### 5.2 历史快照 `history.jsonl`

每行是一条成功采集的额度快照：

```json
{"schema_version":1,"provider_id":"minimax","recorded_at":"2026-07-22T11:11:36+08:00","windows":[{"model_id":"general","window_id":"5h","remaining_pct":76.0,"reset_at":"2026-07-22T14:20:00+08:00"},{"model_id":"general","window_id":"weekly","remaining_pct":89.0,"reset_at":"2026-07-26T00:00:00+08:00"}]}
```

记录规则：

- 只记录成功的 API 响应；
- 任一百分比或重置时间变化时立即记录；
- 数据无变化时，每 15 分钟最多记录一次心跳快照；
- 保留最近 90 天；
- 每日最多执行一次历史清理；
- 图表读取时忽略格式损坏的单行；
- 读取到不完整的最后一行时忽略该行，不影响当前状态。

该历史表示“本机观察到的剩余额度变化”，不是官方逐次 Token 消耗记录。额度重置时曲线会明显回升。

## 6. 组件职责

### 6.1 PowerShell 采集器

继续负责：

- API Key 解密；
- MiniMax API 调用与重试；
- 响应校验和额度窗口标准化；
- 当前缓存与 Rainmeter 文本缓存写入；
- 历史快照判定、追加和清理；
- 日志与失败降级。

不负责绘图或启动详情窗口。

### 6.2 Rainmeter 皮肤

负责：

- 读取两个窗口的百分比、重置倒计时、状态和更新时间；
- 使用两个 `Roundline`/Shape 圆环展示剩余额度；
- 根据正常、临近耗尽、错误状态改变强调色；
- 点击“查看详情”启动 EXE；
- 保持可拖动、常驻桌面和当前 Rainmeter 行为。

### 6.3 WPF 详情应用

内部保持少量、明确的边界：

- `UsageCacheReader`：读取并验证当前缓存；
- `HistoryReader`：流式读取最近 90 天有效快照；
- `UsageViewModel`：计算状态、倒计时和图表序列；
- `CircularGauge`：绘制可复用圆环；
- `TrendChart`：绘制剩余额度折线与时间轴；
- `MainWindow`：组合详情界面与刷新行为。

不引入依赖注入容器、数据库、Web 服务或大型 UI 框架。

## 7. 交互与视觉规则

### 7.1 状态颜色

- 正常：蓝色 5 小时环、紫色周环；
- 剩余低于 20%：对应圆环切换为橙色；
- 剩余低于 10%：对应圆环切换为红色；
- 数据过期或请求失败：状态文字为橙色，但保留最后有效圆环值；
- 没有有效数据：显示中性灰占位，不显示 `0%` 误导用户。

### 7.2 详情窗口刷新

- 启动时立即读取当前缓存与历史；
- 窗口打开期间每 15 秒重新读取本地缓存；
- “刷新数据”按钮调用现有 `Update-MinimaxUsage.ps1` 执行一次采集，等待其结束后重新读取缓存；
- 手动刷新设置执行中状态与超时，禁止重复启动多个采集进程；
- WPF 不实现第二套 HTTP/API Key 逻辑，所有联网采集仍统一经过 PowerShell。

### 7.3 趋势图

- 默认打开 7 天视图；
- 可切换 24 小时、7 天、30 天；
- 5 小时和本周额度使用与圆环一致的颜色；
- 百分比纵轴固定为 0–100%；
- 数据间隔过大时不伪造连续精确消耗；
- 图表旁明确说明数据是本机快照。

## 8. 错误处理

### 8.1 API 请求失败

- 保留最后一次成功额度；
- `cache.json` 写入错误状态和错误信息；
- Rainmeter 显示错误/过期状态，但圆环保持最后值；
- WPF 展示简洁错误说明和最后成功更新时间。

### 8.2 数据过期

最后成功更新时间超过 3 分钟时：

- 显示“数据已过期”；
- 不把旧数据当成实时数据；
- 保持历史趋势和最后有效额度可见。

### 8.3 API Key 或首次安装问题

- 无有效缓存时显示配置指引；
- API Key 无效时明确提示重新运行 `Set-MinimaxApiKey.ps1`；
- EXE 不提供输入或保存 API Key 的入口。

### 8.4 缓存或历史损坏

- 当前缓存无法解析时显示“缓存不可用”，不崩溃；
- 历史单行损坏时跳过并继续；
- 历史全部不可用时只隐藏趋势，当前额度仍正常显示；
- 所有失败写入现有日志文件。

## 9. 安装与交付

- WPF 发布目标为 `.NET 8 / win-x64 / self-contained / single-file`；
- 用户不需要安装 .NET、Node.js 或 Python；
- EXE 放在项目可预测的发布目录；
- Rainmeter 皮肤通过变量文件引用 EXE 与缓存位置，避免把开发机绝对路径写死在皮肤中；
- 安装脚本负责写入项目路径、复制或更新皮肤以及注册任务计划；
- 卸载时删除任务计划和皮肤，是否保留历史数据由用户决定。

首版不制作 MSI/MSIX 安装包，继续使用项目现有 PowerShell 安装方式，减少范围。

最终还需在 Windows 10 x64 环境执行真实验证：

## 11. 成功标准

本阶段完成的判定标准：

1. 桌面小组件以两个并列圆环正确显示 5 小时和本周剩余额度；
2. 百分比、重置时间和 MiniMax API 数据一致；
3. 点击小组件能打开独立详情 EXE；
4. 详情窗口视觉方向与已确认的参考效果一致；
5. 详情窗口显示 24 小时、7 天、30 天本机额度趋势；
6. 关闭详情窗口后应用完全退出；
7. API 失败或数据过期时不归零、不静默，并保留最后有效数据；
8. API Key 不进入 Rainmeter 或 WPF 进程；
9. Windows 10 x64 用户无需安装额外运行环境；
10. 首版只显示 MiniMax，代码中不出现无数据的其他服务占位实现。
